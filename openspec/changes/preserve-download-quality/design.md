## Context

下載完成後，程式以 ffprobe 探測檔案並用一份固定白名單決定「容器 remux」或「重新編碼」。白名單只認 H.264 視訊、AAC 或無音訊、偶數尺寸。

Facebook 對 Reel 供的格式（2026-07-30 對真實 Reel 實測）：DASH 視訊階梯**只有 AV1**（最高 1080x1920），H.264 只存在於 progressive 的 `hd`（720x1280）與 `sd`（360x640）。yt-dlp 預設挑最佳品質，因此每支 Reel 下載到的都是 AV1，白名單必然失敗，全部走重新編碼。

重新編碼的實測代價（18.5 秒 Reel）：輸出 9.93 MB 對來源 6.50 MB（大 53%）、後處理 6 秒對 remux 的 0.03 秒（慢 200 倍）、SSIM 0.9847（有可測量的世代損失）。AV1 比 H.264 效率高，所以轉成 H.264 必然膨脹。

音訊則是無條件重新編碼為 AAC 128k，即使來源已是 AAC 59959 bps —— 檔案變大、音質二次壓縮。

## Goals / Non-Goals

**Goals:**

- 讓來源已是 AAC 的音訊不再被二次壓縮。
- 讓平台能解碼的原始視訊可以直接使用，不必為了相容性付出畫質、體積與時間三重代價。
- 讓「相容性」與「保留原始畫質」成為使用者可見、可覆寫的選擇，而不是寫死的假設。
- 平台能力判斷錯誤時，錯向保守的一邊（產出能播的檔案）。

**Non-Goals:**

- **不改變下載時挑選哪個格式。** 目前不指定 format selector，由 yt-dlp 挑最佳品質。改抓 progressive 的 `hd` 可得到 H.264 且到處能播，但解析度由 1080x1920 降到 720x1280，實測放大後對照原檔的 SSIM 為 0.9600 —— **比現行重新編碼的 0.9847 更差**，因此它不是畫質解法，而是另一種「速度與相容優先」的取捨，獨立成另一個變更。
- **不把 remux 適用範圍開放給所有 codec。** 只擴充到 AV1。VP9 雖然在 MP4 中合法，但支援度差；納入會讓可播性更難預測。
- **不做輸出檔的實際播放驗證。** 程式無法知道使用者最終在哪個裝置、哪個播放器開啟該檔案。
- **不實作 Windows 的 Media Foundation 查詢。** 見下方對應決策：需要額外依賴，且無法在 macOS 上編譯或測試行為。獨立成另一個能在 Windows 或 CI 上真正驗證的變更。
- 不改動 remux 與重新編碼各自的 ffmpeg 參數組成（除音訊那一項），也不改動 CPU 許可的取得規則。

## Decisions

### 平台能力偵測回傳三態，只有明確的「可以」算支援

偵測結果為「可以」、「不行」、「未知」三態，而非布林值。Linux 無法得知使用者用哪個播放器，只能回「未知」；把它壓成布林會迫使我們在兩個都不誠實的答案之間選一個。

決策時只有「可以」被視為支援，「不行」與「未知」一律走重新編碼。錯判的方向因此固定為「產出能播但較大較慢的檔案」，而不是「產出播不出來的檔案」。

### macOS 用 VideoToolbox 的硬體解碼查詢，並接受它低估軟體解碼

macOS 端查詢 VideoToolbox 是否支援該 codec 的硬體解碼。這個查詢只回答硬體能力，因此具備軟體解碼能力但無硬體支援的機器會被判為「不行」而走重新編碼。

Alternatives considered:

- **實際解碼一小段樣本來驗證。** 已排除 —— 需要在程式內嵌測試樣本並跑一次解碼，成本與複雜度都高於它換來的準確度，且仍然只反映本機而非播放裝置。
- **依 macOS 版本與晶片型號推論。** 已排除 —— 需要維護一張隨新機型與新系統版本過期的對照表，而 VideoToolbox 查詢本身就是系統給的答案。

低估是可接受的，因為使用者可以手動選擇保留原始畫質。

### Windows 與 Linux 現階段一律回「未知」

除 macOS 以外的平台都走同一個預設實作，直接回「未知」，因此一律走重新編碼並維持本變更前的行為。

Linux 是原理上的限制：系統層面沒有一個能代表「使用者的播放器能不能解」的答案。

Windows 是刻意延後。理想做法是列舉 Media Foundation 是否存在該 codec 的解碼器（Windows 11 24H2 之後內建 AV1，較早版本需使用者自行安裝擴充套件，所以該查詢會如實反映機器狀態），但 `MFTEnumEx` 是 COM API，需要額外依賴，且此專案的 Windows target 無法在 macOS 上編譯 —— 實測 `cargo check --target x86_64-pc-windows-msvc` 會在 `ring` 的 C 編譯階段因找不到 `assert.h` 而失敗。寫下無法在本機編譯也無法測試行為的 COM 程式碼，比誠實地回「未知」更糟：後者只是少拿到改善，前者可能產出播不了的檔案。

Alternatives considered:

- **以 Windows build 編號推論（24H2 以後視為支援）。** 已排除 —— 與本設計拒絕「維護會過期的版本對照表」的理由相同，用在 Windows 上會自相矛盾。
- **呼叫 powershell 查 AV1 Video Extension 套件是否存在。** 已排除 —— Windows 11 24H2 以後內建 AV1 而不需該套件，因此最大宗的 Win11 使用者會被低估。方向雖安全但等於白做。

### 處理策略是三值設定，`auto` 於每次下載時解析

設定值為 `auto`、`original`、`compat`，預設 `auto`。

`auto` 不把偵測結果烘進設定的預設值，而是在每次後處理決策時解析。若把結果寫成預設值，使用者換機、升級系統或安裝解碼器之後，儲存的值就會與實際能力脫節，而使用者不會知道要去改它。

設定介面須顯示 `auto` 當下解析到的結果，否則使用者無法得知 `auto` 實際選了哪條路。

Alternatives considered: 只做兩值（保留原檔／相容）並用偵測決定預設。已排除 —— 預設值一旦寫入資料庫就固定了，等同於把一次性的偵測結果變成永久設定。

### 偵測結果於 process 內只查一次

偵測結果在單一 process 生命週期內固定，第一次需要時查詢後快取。平台的解碼能力不會在程式執行中改變（安裝解碼器套件需要重啟應用程式才會被 Media Foundation 反映），而 Media Foundation 的列舉不是零成本，不應每支下載都跑一次。

### remux 適用範圍只擴充到 AV1，且沿用既有的音訊與尺寸條件

可直接 remux 的視訊 codec 為 H.264（既有）與 AV1（新增）。音訊仍須為 AAC 或無音訊，尺寸條件沿用既有規則。AV1 在 MP4 中的 codec tag 為 `av01`，ffmpeg 以串流複製寫出時會正確帶上（已實測確認）。

策略為 `original` 但視訊 codec 不在此清單內時，退回重新編碼而非產出可播性不明的檔案。

### 音訊在來源已是 AAC 時直接複製

重新編碼路徑中，若探測到的音訊 codec 已是 AAC 則直接複製，否則轉為 AAC。判斷所需的欄位已存在於探測結果中，目前只被用於白名單判定。

此項與視訊策略無關，也不受設定影響 —— 把已是 AAC 的音訊再壓一次沒有任何情境下是更好的選擇。

## Implementation Contract

**In scope:** 平台能力偵測模組（三平台）、處理策略設定項與其設定介面（含 `auto` 解析結果的顯示）、後處理決策改為白名單與策略共同決定、音訊在已是 AAC 時直接複製。

**Out of scope:** Non-Goals 所列四項。

**Behavior**

- 來源音訊已是 AAC 時，輸出的音訊串流與來源位元相同；來源音訊非 AAC 或無法探測時，仍轉為 AAC。
- 策略為 `compat` 時，行為與本變更前完全相同（除音訊那一項）。
- 策略為 `original` 且視訊 codec 為 H.264 或 AV1、音訊為 AAC 或無音訊、尺寸符合既有條件時，後處理為串流複製，輸出視訊與來源位元相同。
- 策略為 `original` 但視訊 codec 不在可 remux 清單內時，走重新編碼。
- 策略為 `auto` 時，平台對該視訊 codec 回答「可以」則等同 `original`，回答「不行」或「未知」則等同 `compat`。
- Linux 上 `auto` 一律等同 `compat`。
- 設定介面顯示 `auto` 當下解析到的結果。
- 走 remux 的任務依既有規格不佔用 CPU 編碼名額，因此策略放寬後編碼名額的競爭下降。

**Interface / data shape**

- 新增模組對外提供一個查詢操作：輸入為視訊 codec 名稱（與 ffprobe 的 `codec_name` 同一組字串，例如 `h264`、`av1`），輸出為「可以／不行／未知」三態。比較須不分大小寫。
- 該模組每個平台一個實作，以條件編譯選擇；不支援的平台走回傳「未知」的預設實作。結果在 process 內快取。
- Settings 結構新增一個字串欄位承載處理策略；合併邏輯以允許清單驗證（`auto`、`original`、`compat`），不在清單內時保留預設值且不回寫資料庫 —— 與既有主題欄位一致。前端 Settings 介面同步新增，型別為三值聯集。
- 後處理決策函式的簽章擴充為同時接受探測結果、處理策略與平台能力查詢結果，回傳既有的 remux 或重新編碼兩種計畫。決策必須是純函式以便測試，平台查詢的結果由呼叫端傳入而非在函式內查詢。

**Failure modes**

- 平台查詢失敗、拋出例外或無法載入系統框架時，視為「未知」而非「可以」。
- 探測結果無法解析時，維持既有行為：走重新編碼。
- 設定值不在允許清單內時保留預設 `auto`，不回寫資料庫；此為刻意靜默，與既有主題欄位一致。
- remux 失敗時維持既有行為：回傳含 ffmpeg 實際輸出的錯誤並清理暫存檔，不自動退回重新編碼（自動退回會讓使用者無法察覺原檔有問題）。

**Acceptance criteria**

- 單元測試涵蓋決策函式的策略矩陣：三種策略 × 三種平台答案 × 視訊 codec 為 H.264／AV1／其他，斷言各自的計畫。
- 單元測試涵蓋音訊決策：來源 AAC 時為複製、非 AAC 時為轉碼、無音訊時不產生音訊參數。
- 單元測試涵蓋設定值的允許清單：三個合法值各自被接受，不合法值保留預設 `auto`。
- 單元測試涵蓋 codec 名稱比較不分大小寫。
- 手動驗收：在偵測到支援 AV1 的機器上以 `auto` 下載一支 Reel，確認後處理狀態文字為容器最佳化、輸出檔的視訊 codec 為 `av1`、檔案大小接近下載到的原檔、耗時遠短於重新編碼。
- 手動驗收：同一支 Reel 以 `compat` 下載，確認輸出視訊 codec 為 `h264`，且音訊位元率與來源相同（驗證音訊未被重新編碼）。
- 手動驗收：設定介面顯示 `auto` 解析到的結果，且切換三個值後說明文字隨之變化。

## Risks / Trade-offs

- **既有使用者的預設輸出格式改變** → 在偵測到支援 AV1 的機器上，`auto` 會產出 AV1 而非 H.264。畫質更好、檔案更小、幾乎瞬間完成，但帶到不支援 AV1 的裝置上無法播放。設定介面須說明此取捨並提供切換到 `compat` 的途徑；發佈說明須載明此變更。
- **偵測只反映下載這台機器，不反映播放裝置** → 這是本方案的根本限制。使用者可能 AirDrop 到手機、複製到其他電腦、上傳到其他服務，而那些環境的能力無從得知。因此 `auto` 只是預設值的選擇而非保證，且必須可覆寫。**不得**把偵測結果當成「這個檔案到處都能播」的證明。
- **macOS 的查詢低估軟體解碼能力** → 有軟體解碼但無硬體支援的機器會被判為「不行」而走重新編碼，得到較差的畫質。方向是安全的（檔案仍能播），且使用者可手動選 `original`。
- **Windows 的答案會隨使用者安裝解碼器而改變，但快取到重啟才更新** → 安裝 AV1 擴充套件後需重新啟動應用程式才會被偵測到。此行為與既有的 CPU 並行度設定一致（都是 process 生命週期內固定），設定介面的說明須涵蓋。
- **Windows 與 Linux 使用者拿不到本變更的畫質改善** → 兩者都回「未知」因而走重新編碼，行為與變更前相同。使用者仍可手動選 `original` 取得原檔畫質；設定介面的說明須讓這件事可被發現。Windows 的自動判斷待另一個變更補上。

## Migration Plan

- 無資料庫 migration。新設定項由 Settings 的預設值補齊，既有安裝首次讀取即得到 `auto`。
- 既有安裝的可觀察行為變更：在支援 AV1 的機器上，下載 Facebook Reel 的輸出由 H.264 變為 AV1。使用者若需要既有行為，將設定改為 `compat` 即可，無須重新下載已完成的檔案。
- 回滾：設定項未被讀取時不影響既有資料；還原程式碼即可，已產出的 AV1 檔案不受影響（仍可播放於支援的環境）。

## Open Questions

- macOS 是否值得補上軟體解碼能力的判斷（例如以系統版本為輔助條件），以免有軟解能力的機器被低估。目前選擇不做，因為錯判方向安全且使用者可覆寫；若實際回報顯示大量機器被低估，再依回報調整。

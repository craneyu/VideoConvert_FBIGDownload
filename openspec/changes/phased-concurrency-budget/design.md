## Context

VidBridge 有兩條各自獨立的 ffmpeg 管線：下載流程在 yt-dlp 結束後接一段後處理（依 ffprobe 結果決定 remux 或重新編碼），轉檔頁籤則是另一條完全獨立的重新編碼管線。兩者都不知道對方在做什麼，而 libx264 本來就會吃滿所有可用核心，因此兩個並行的重新編碼是把彼此砍半，不是加總吞吐。

目前的並行控制全在前端：一個固定為 2 的常數決定同時有幾個下載在跑，側邊欄另外硬寫了一份顯示文字。轉檔則完全沒有上限 —— 每個任務各有一顆手動啟動按鈕，連點五次就同時開五個 ffmpeg 行程。

兩個命令都宣告為 async 卻在內部做同步阻塞 I/O（逐行讀取子行程輸出、等待其結束），因此整趟工作期間佔住一個 async runtime 的 worker。

設定以 key-value 表儲存，並經由 Settings 的合併邏輯讀出後套用預設值，因此新增設定項不需要資料庫 migration。

## Goals / Non-Goals

**Goals:**

- 讓「下載後處理」與「轉檔」兩條管線的重新編碼受同一個上限約束，使並行度成為有意義的旋鈕而非會反噬的旋鈕。
- 把並行上限從前端常數與硬寫顯示文字收攏成單一設定來源。
- 讓長時間執行的命令不再佔用 async runtime 的 worker。
- 讓「已下載完成但在排隊等編碼」這個新出現的等待狀態對使用者可見。

**Non-Goals:**

- **不做下載時的 H.264 偏好選擇，也不放寬 remux 白名單。** 這是討論中識別出的最大實際加速槓桿，但形狀尚未確定：需要先對真實的 Facebook Reel 執行 yt-dlp 的格式列出動作，確認是否存在可選的 avc1 格式。若存在則是格式選擇；若只有 av01 則變成放寬白名單接受 AV1-in-MP4，而後者風險高得多（AV1 硬解在較舊 macOS 與非 Apple Silicon 機器上不存在，remux 出來的檔案可能無法播放）。另外偏好 H.264 會壓低 YouTube 的解析度上限，必須限定平台或做成明確取捨。獨立成另一個 change。
- **不引入 aria2c 單檔多連線加速。** 需要第三個外部依賴進入依賴檢查與自動安裝流程，且實測顯示 yt-dlp 的分段並行參數對 YouTube VOD 無效（每個格式的協定欄位皆為 https，無分段可並行）。獨立成另一個 change，且將是預設關閉的選配。
- **不做取消／中止正在執行的任務。** 涉及子行程終止與暫存檔清理的語意，是另一個獨立的接縫，且本 change 的任務量已接近上限。
- 不改動現有判斷 remux 或重新編碼的邏輯本身，只改動該決策結果被如何用於取得許可。

## Decisions

### 阻塞工作以 spawn_blocking 移出 async runtime

保留兩個命令的 async 宣告，在內部把阻塞區段包進 Tauri 的 spawn_blocking 並 await 其結果。

Alternatives considered:

- **改為純同步命令。** 已排除。讀 tauri-macros 的 command wrapper 可知，未標註 async 的函式走 Blocking 執行情境，會在 IPC 執行緒上同步跑完 —— 比現況更糟，會直接凍住 IPC。
- **在同步函式上標註 async 屬性。** 已排除。該 macro 產生的 kind 字串雖為 sync_threadpool，但實際產生的程式碼是把函式呼叫放進一個 async 區塊後交給 respond_async_serialized，而後者最終呼叫 async_runtime 的 spawn —— 仍是 tokio task，工作照樣佔用 worker。這個命名容易誤導，是此決策必須寫明理由的原因。

### 網路並行度留在前端，Rust 只擁有 CPU 許可池

前端本來就控制同時發出幾個下載命令，那就是網路並行度，無須在 Rust 再複製一份計數。Rust 端只擁有一件事：CPU 許可池。

這是接縫深度的判準所在。一個只做計數的 Rust 排程器刪掉後不會有東西壞掉（前端本來就在計數），因此不該存在；而擁有跨管線 CPU 預算的模組刪掉後，兩條管線的重新編碼會同時吃滿所有核心 —— 通過刪除測試。兩條管線都無法自行知道對方此刻在編碼，這個資訊只存在於共用的許可池裡。

### CPU 許可池由下載後處理與轉檔共用

單一許可池置於 Tauri 的受管理狀態中，下載命令的後處理階段與轉檔命令都向同一個池取得許可。取得為非阻塞式等待（async），因此等待中的任務不佔用 worker。

### 容器 remux 不取得 CPU 許可

remux 是串流複製，不解碼也不編碼，成本接近純 I/O。下載流程已先以 ffprobe 判定該檔要走 remux 或重新編碼，因此僅在判定為重新編碼時取得 CPU 許可；判定為 remux 則直接執行。

Alternatives considered: 讓所有後處理一律取得許可。已排除 —— 會讓兩個原本近乎瞬間完成的 remux 無謂地排隊，把便宜的操作按昂貴的操作計價。

### 分階段許可：網路階段結束即釋放，不被 CPU 等待佔用

下載命令是「網路階段接 CPU 階段」的組合。若一個已下載完成、正在等待 CPU 許可的任務在前端仍被計為「下載中」，它就會佔住一個網路名額不放，讓後面的下載無法開始。

因此下載命令在進入 CPU 等待前先發出狀態事件，前端據以把該任務移出「下載中」的計數並重新驅動佇列，讓下一個下載立刻開始。這使網路名額與 CPU 名額成為兩筆分別計價的資源。

### 新增「等待編碼」任務狀態

上一個決策使「已下載完成但尚未開始編碼」成為一個真實且可能持續數分鐘的狀態。沒有對應的顯示，多支任務會同時停在下載階段的進度上限值不動 —— 而單一個不動的後處理進度事件已經被使用者讀成當機過一次，那正是後處理進度回報存在的原因。

沿用既有的下載進度事件與其狀態文字欄位承載這個狀態，不新增事件通道 —— 該欄位目前已被用來承載 remux 與重新編碼兩種階段的說明文字，是同一種用法。

### 預設網路 3、CPU 1，CPU 上限 2

網路並行度預設 3、可設定範圍 1 到 8。CPU 並行度預設 1、可設定範圍僅 1 到 2，且設定介面須說明第二個名額的用途是「讓程式保持回應」而非「更快」—— 因為並行的兩個 libx264 是把彼此砍半而非加總吞吐。上限不由核心數推導，理由同上。

CPU 許可池在**第一次需要許可時**依設定建立，之後於整個 process 生命週期固定不變。因此該設定的變更於下次啟動生效，設定介面須明說這一點。網路並行度由前端佇列即時讀取，變更立即生效。

之所以不是「啟動時建立」：資料庫連線是由前端呼叫載入時才建立的，migrations 也在那時才執行，所以 Tauri 的 setup 階段既讀不到 settings 表也可能還沒有該表。若在 setup 階段硬讀，結果會是每次啟動都只能拿到預設值，使用者設定的值被靜默忽略 —— 那比延後讀取糟得多。延後到第一次編碼時讀取，此時前端早已完成載入，取得的是權威來源的值。

Alternatives considered:

- **讓 CPU 上限可即時縮放。** 已排除 —— 縮小許可池需要處理已發出許可的回收語意，而該設定只有兩個可能值，重新啟動的代價遠低於這個複雜度。
- **由前端在啟動後主動把上限推給後端。** 已排除 —— 等同於把池變成可重建，且無法保證推送早於第一個下載完成其網路階段，順序一旦顛倒就會用錯的容量建池。

## Implementation Contract

**In scope:** CPU 許可池模組、兩個命令的 spawn_blocking 改造與許可取得、兩個並行度設定項及其設定介面、前端下載佇列改讀設定值、前端轉檔佇列、「等待編碼」狀態的發出與顯示、側邊欄顯示改讀實際值、README 該行改寫。

**Out of scope:** Non-Goals 所列的四項。

**Behavior**

- 同時排入多支影片時，實際開始下載的數量等於網路並行度設定值；其餘保持等待。
- 任一下載完成其網路階段後立即釋放網路名額，下一個等待中的下載隨即開始 —— 即使前者尚未開始編碼。
- 需要重新編碼的後處理，以及轉檔任務，兩者加總同時執行的數量不超過 CPU 並行度設定值；超出者進入等待。
- 判定為 remux 的後處理不受 CPU 並行度約束，直接執行。
- 等待 CPU 許可的下載任務顯示「等待編碼」，而非停在不動的進度數字上。
- 轉檔頁籤同時執行的任務數不超過 CPU 並行度設定值；超出者顯示為等待而非立刻開新行程。
- 側邊欄的並行任務限制顯示兩個設定的實際值。
- 兩個命令執行期間，設定讀寫與歷史查詢等其他 IPC 呼叫仍可正常回應。

**Interface / data shape**

- 新增一個 Rust 模組持有 CPU 許可池，置於 Tauri 受管理狀態；對外提供一個 async 的取得許可操作，回傳一個在釋放時歸還許可的守衛值。取得操作接受一個上限值，但只有第一次呼叫會用到它來建池，後續呼叫的傳入值一律被忽略 —— 這個「首次決定」語意必須寫在該操作的文件註解裡，否則呼叫端會誤以為每次都能改變上限。
- 兩個命令改為額外接收資料庫狀態，以便讀出 CPU 上限設定。讀取失敗（資料庫尚未載入）時退回預設值而非讓下載或轉檔失敗。
- Settings 結構新增兩個無號整數欄位，分別代表網路並行度與 CPU 並行度；合併邏輯為兩者各自解析字串並做範圍檢查，超出範圍時保留預設值且不回寫資料庫 —— 與既有主題欄位的允許清單做法一致。前端的 Settings 介面同步新增這兩個欄位。
- 下載進度事件的既有負載形狀不變。新增一個狀態文字常數代表「等待編碼」，於進入 CPU 等待前隨進度事件發出，進度值為下載階段的既有上限值。
- 前端下載任務的狀態集合新增一個代表「等待編碼」的值，且該值不計入「下載中」的並行計數。
- 前端轉檔任務沿用既有狀態集合並新增一個代表等待的值。

**Failure modes**

- 取得許可失敗（許可池已關閉）視為錯誤回傳，不得靜默略過而在無許可的情況下開始編碼。
- spawn_blocking 的工作若 panic，命令須回傳錯誤字串而非讓整個 runtime 中止。
- 設定值為非數字或超出範圍時保留預設值，且不回寫資料庫；此情形為刻意靜默，與既有主題欄位一致。
- 既有的失敗路徑行為不變：子行程的 stderr 尾段仍須在失敗時回傳，暫存檔仍須清理。

**Acceptance criteria**

- 單元測試涵蓋設定值的解析與範圍檢查：合法值、非數字、低於下限、高於上限，各自的結果。
- 單元測試涵蓋「remux 不取得 CPU 許可、重新編碼才取得」的判定，以既有的後處理決策結果為輸入。
- 單元測試涵蓋許可池：上限為 1 時第二個取得動作須等待，前一個守衛釋放後才取得成功。
- 手動驗收：以網路 3、CPU 1 排入五支影片，觀察到最多三支同時下載、其中至多一支在編碼、其餘顯示「等待編碼」，且任一支完成下載後第四支立即開始下載。
- 手動驗收：於轉檔頁籤連續啟動五個任務，觀察到同時只有一個在執行，其餘顯示等待。
- 手動驗收：在一個重新編碼進行中的同時開啟設定頁並修改任一設定，設定頁須正常回應。

## Risks / Trade-offs

- **已下載完成卻在排隊等編碼的任務無法被取消或跳過** → 本 change 以「等待編碼」狀態讓等待可見，使其不被誤讀為當機；取消能力獨立成另一個 change。此風險不構成回歸 —— 現況同樣無法取消，只是原先會立刻開始互相搶 CPU 的編碼。
- **CPU 並行度的變更需重新啟動才生效** → 設定介面明說；該設定僅有兩個可能值，代價有限。
- **側邊欄顯示與實際行為可能再次分歧** → 顯示改為讀取設定值本身，不再存在第二份需要手動同步的來源。
- **spawn_blocking 使用的執行緒池與 CPU 許可池是兩個不同的界限** → 前者只是為了不佔用 async worker，容納量遠大於本專案的並行度；實際的並行約束一律由 CPU 許可池決定，不得改以執行緒池大小充當上限。
- **多支任務同時停在下載階段上限值** → 這是設計的預期結果而非缺陷，由「等待編碼」狀態負責說明；驗收條件已將其列為必須觀察到的現象。
- **調高下載並行度的即時效果無法在使用者流程中被觀察到** → 設定頁是獨立路由，導覽過去會卸載首頁元件，而下載任務清單是元件狀態，因此回來時佇列已清空、沒有待處理任務可被啟動。反應式觸發仍然實作並保留（它是正確的機制，且在佇列能跨導覽存活後就會生效），但目前只在同一次掛載內可觀察。讓佇列跨導覽存活屬於另一個變更的範圍。
- **等待編碼期間仍佔用一個轉檔／後處理的「已開始」名額，但無法取消** → 見上方取消能力的風險；此變更只讓等待可見。
- **前端與後端共用一個狀態文字字面值**（「已下載完成，等待編碼中...」）→ 進度事件的負載形狀刻意不變，因此階段資訊由狀態文字承載。若後端改字而前端沒跟著改，下載會停在下載階段上限值且佇列不再推進。兩端都以註解互相指名，且該字串在前端是唯一具名常數而非散落的字面值。

## Migration Plan

- 無資料庫 migration。兩個新設定項由 Settings 的預設值補齊，既有安裝在首次讀取時即取得預設值。
- 既有安裝的可觀察行為變更：同時下載數由 2 變為 3（網路），而重新編碼由「最多兩個同時進行」變為預設一次一個。後者在多任務情境下是總時間縮短，但單一任務的開始時間可能延後，這正是「等待編碼」狀態存在的原因。
- 回滾：兩個設定項未被讀取時不影響既有資料；還原程式碼即可，無需清理資料。

## Open Questions

- 網路並行度預設 3 是依「網路平行度便宜」推論而來，未在慢速連線上實測。若實測顯示 3 個並行下載反而使個別任務的失敗重試變多，此預設值應下調；此為上線後可依實測調整的參數，不阻擋實作。

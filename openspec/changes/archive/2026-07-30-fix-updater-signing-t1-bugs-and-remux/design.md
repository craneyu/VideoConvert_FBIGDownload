## Context

VidBridge 是 Tauri 2 + SvelteKit 桌面應用，Rust 後端透過外部 `yt-dlp` 與 `ffmpeg` 執行下載與轉檔，下載歷史存於 SQLite（透過 tauri-plugin-sql，migration 定義在 `src-tauri/src/lib.rs`）。目前版本 0.1.3，最後一次發佈於兩個月前。

本次要修的三組問題各自的現狀：

- **自動更新**：`src-tauri/tauri.conf.json` 的 updater 設定中，公鑰欄位放的是 passphrase 加密的 minisign 私鑰（base64 解碼後註解為 rsign encrypted secret key，內容含 KDF salt 與 opsLimit/memLimit 欄位，公鑰檔案不含這些）。endpoint 指向 GitHub raw 上一個從未進入版控的 manifest 檔案。前端更新檢查的 catch 為空。三者相加的結果是自動更新從未成功，也從未有錯誤徵兆。
- **前端事件監聽**：`src/routes/+page.svelte` 在 `onMount` 中以 async 函式註冊三個事件監聽並回傳 cleanup。Svelte 5 中 `onMount` 回傳 Promise 時 cleanup 不會被呼叫，svelte-check 亦獨立回報此型別錯誤。
- **下載後處理**：下載完成後無條件以 libx264 重新編碼一次，理由是相容性；來源檔實際上多已符合相容條件。

已驗證的環境事實：SQLite 的 `CURRENT_TIMESTAMP` 回傳 UTC（實測 07:22 對本地 15:22，差 8 小時）；`cargo check` 目前無警告；`cargo test` 有 2 個既有測試通過。

專案慣例：全域偏好要求時間一律使用本地時間（Local time），不做 UTC 與本地的來回轉換。

## Goals / Non-Goals

**Goals:**

- 自動更新可實際運作：以真正的公鑰驗簽、manifest 可被取得、失敗時可觀測。
- 舊簽章私鑰停止使用，且新私鑰不以任何形式進入版控。
- 六個使用者可見缺陷有可驗證的修復，且每項都能指名觀察到的行為變化。
- 下載後處理在來源已相容時不再重新編碼，且走了哪條分支對使用者與測試皆可觀察。
- 下載歷史的時間顯示與紀錄狀態正確，既有資料一併校正。

**Non-Goals:**

- 不新增獨立的測試 CI workflow（在推送與 PR 時跑測試）。僅調整既有發佈 workflow 的觸發條件，避免與 proposal 的影響範圍不一致。
- 不處理其他效能項：啟動時無條件執行套件管理器升級、工具路徑解析未快取、依賴檢查為同步命令、每次下載呼叫 yt-dlp 三次。
- 不處理工程衛生項：CSP 設定、檔案系統權限範圍、原生 alert 與 confirm 改為應用內提示、模板殘留死碼、Rust 端改用 log plugin。
- 不實作既有 spec 已定義但尚未實作的功能：任務暫停與取消、批量網址輸入、下載畫質與格式選擇、bitrate 與 FPS 控制、系統列快速下載與進度摘要。
- 不改變下載歷史的資料存取架構（webview 直接執行 SQL 的現狀保留）。
- 不將 ffmpeg 與 yt-dlp 打包進安裝檔。
- 不處理 macOS 公證與開發者簽章。

## Decisions

### 輪替簽章金鑰並改填公鑰

產生全新的 minisign 金鑰對。updater 設定的公鑰欄位改為填入公鑰檔的內容；新私鑰與其 passphrase 只存放於 GitHub Secrets，不寫入 repo 的任何檔案（包含設定檔、workflow、文件）。舊金鑰視為已洩漏並永久停用。

*替代方案*：沿用舊金鑰只修 manifest 路徑 —— 否決。私鑰已進入公開版控，無法證明未被取走；且既有自動更新本來就不能運作，沒有相容性理由保留它。

金鑰產生與 Secrets 設定必須由人工執行，實作代理無法完成，因此這是 A 組其餘驗證動作的前置阻擋條件。

### 更新 manifest 檔名與 endpoint 對齊

endpoint 改為指向 GitHub Releases 資產上由發佈流程自動產生的 manifest，而非 GitHub raw 上手動維護的檔案。發佈工具會在每次發佈時產生帶正確版本號與簽章的 manifest，兩者名稱必須一致。

*替代方案*：繼續手動維護 main 分支上的 manifest —— 否決，每次發佈都要人工同步版本與簽章字串，正是目前失效的原因。

附帶約束：指向「最新發佈」的資產 URL 不會解析到 draft 或 pre-release。目前 0.1.0 與 0.1.1 為 draft、0.1.2 與 0.1.3 為 pre-release，因此發佈設定需產出正式 release，否則 manifest 仍然取不到。

### 更新檢查失敗改為寫入 log

更新檢查的 catch 不再是空的，至少寫入錯誤 log。不彈出對話框，避免每次啟動都對使用者產生噪音。目的是讓「自動更新再次失效」這件事有徵兆可查，而非靜默兩個月。

### release workflow 改由版本 tag 觸發

`.github/workflows/release.yml` 的觸發條件由推送 main 改為推送版本 tag，並加入手動觸發。現狀每次推送 main 都會重跑三平台建置（約 9 至 10 分鐘）並把產物重複上傳到既有 release，因為 tag 名稱取自設定檔版本號，版本沒變 tag 就不變。近五次執行皆為成功，所以這是浪費而非故障。

### 事件監聽改用 effect 管理生命週期

把下載進度、轉檔進度、檔案拖放三個事件監聽從 async `onMount` 移出，改以 `$effect` 註冊並回傳同步 cleanup。由於註冊本身是 async，effect 內需以旗標記錄是否已被銷毀：若 unlisten 在 cleanup 之後才取得，取得時立即呼叫。不需要 cleanup 的初始化邏輯（資料庫載入、依賴檢查、更新檢查）留在 `onMount`。

*替代方案*：保留 `onMount` 但改為非 async 並自行管理 unlisten 陣列 —— 可行，但 `$effect` 是 Svelte 5 慣用做法，且與同檔案既有的剪貼簿偵測 effect 一致。

### 下載失敗時寫回歷史紀錄狀態

下載流程的錯誤處理除了更新前端任務狀態，還要把 `download_history` 對應紀錄的狀態寫為失敗。需處理紀錄尚未建立就失敗的情形（例如取得影片資訊階段就失敗，此時尚無資料列），該情形只更新前端狀態、不執行資料庫寫入。

### 以新增 migration 校正時間戳為本地時間

新增 migration（版本 3），把 `download_history` 的 `created_at` 預設值改為本地時間，並校正既有資料。既有 migration 不得修改 —— 既有安裝已執行過版本 1，改動不會重跑。

SQLite 無法直接變更欄位預設值，因此以「建新表、複製資料、丟舊表、改名」的方式重建。既有資料的校正使用 SQLite 的 `datetime` 搭配 localtime 修飾詞把儲存值由 UTC 轉為本地時間，不寫死時區位移，以免在非台灣時區的機器上算錯。

預設值變更與既有資料回填必須屬於**同一個 migration 版本**，不得拆成兩個版本或兩次發佈。若預設值先改為本地時間而回填尚未執行，資料表會同時存在 UTC 與本地時間的資料列，且欄位本身不帶時區資訊，事後無法分辨哪些列已轉換 —— 這種混合狀態沒有安全的修復路徑。

*替代方案*：只改為在寫入時明確帶入本地時間、不動資料庫預設 —— 否決作為單獨方案，因為既有資料仍然是錯的。

### 開啟檔案位置改為跨平台實作

`open_folder` 目前整段包在 macOS 條件編譯內，其他平台直接回傳成功但什麼都不做，而發佈流程確實在建置 Windows 安裝檔。改為三平台皆有實作：優先使用既有的 opener plugin 所提供的「在檔案管理器中顯示項目」能力；若該能力不足以涵蓋，則按平台分支處理，並同步補上所需的權限識別碼。

### H.265 輸出加上 hvc1 容器 tag

轉檔選擇 H.265 時，輸出容器為 MP4 但未設定容器 tag，產出的 codec tag 為 hev1，QuickTime 與 macOS 預覽皆無法播放。加上 `hvc1` tag 修正。同時明確指定音訊編碼器，移除對「輸出容器預設編碼器」的隱含依賴 —— 這不是修 bug，是讓輸出可預期。

### 讀取並回傳 yt-dlp 的 stderr

下載時 stderr 被設為管線但從未讀取，輸出量超過管線緩衝時子行程會阻塞，下載永久卡住。改為另開執行緒讀取 stderr，以固定容量的環形緩衝保留最後若干行（避免無上限累積記憶體），失敗時把這些行併入回傳的錯誤訊息，取代目前的硬編碼字串。

### 以 ffprobe 判斷後決定 remux 或重新編碼

下載完成後先以 `ffprobe` 取得影像編碼、音訊編碼與畫面尺寸。只有在條件全部滿足時才走容器 remux：影像為 `h264`、音訊為 `aac` 或無音訊軌、寬與高皆為偶數。其餘情形一律走既有的重新編碼路徑，該路徑保留不刪。

remux 使用串流複製搭配 faststart，不重新編碼，因此接近瞬間完成且無畫質損失。走了哪條分支必須反映在下載進度事件的文字上，讓使用者與驗收都能觀察。

*替代方案一*：交給 yt-dlp 的 remux 選項處理 —— 否決，無法回報我們自己的階段進度，且仍需判斷偶數尺寸。
*替代方案二*：完全移除重新編碼路徑 —— 否決，非 h264 來源與奇數尺寸仍需重新編碼才能保證相容。

## Implementation Contract

#### 行為（使用者或維運者可觀察到的結果）

- 從已安裝的舊版本觸發更新檢查時，若存在較新版本，更新流程可完成驗簽並安裝；若失敗，錯誤出現在應用程式 log 中而非無聲消失。
- 在下載頁與設定頁之間往返任意次數後，拖入 N 個影片檔，轉檔清單增加恰好 N 筆任務（目前會隨往返次數倍增）。
- 下載失敗後切到下載歷史頁，該筆紀錄顯示為失敗狀態，而非停留在下載中。
- 下載歷史顯示的日期與該筆下載實際發生的本地日期一致，包含本地時間 00:00 至 08:00 期間建立的紀錄。既有紀錄經校正後同樣正確。
- 在 Windows 與 Linux 點選「開啟檔案位置」會實際開啟檔案管理器並選中該檔案。
- 以 H.265 轉出的 MP4 可在 macOS QuickTime 播放。
- 下載失敗時顯示的訊息包含 yt-dlp 實際輸出的原因（例如影片為私人、需登入、地區限制），而非固定字串。
- 下載一支來源已為 H.264 加 AAC 且尺寸為偶數的影片時，完成階段的進度文字顯示為容器最佳化而非重新編碼，且該階段耗時遠短於重新編碼；輸出檔可正常播放。下載一支非 H.264 來源時仍走重新編碼並成功產出可播放檔案。

#### 介面與資料形狀

- 更新設定的公鑰欄位內容：解碼後必須是 minisign 公鑰（單行金鑰、不含 KDF 欄位、註解不含 secret key 字樣）。
- 更新 manifest 的檔名必須與 updater endpoint 所指向的檔名一致；endpoint 指向 release 資產而非 repo raw 路徑。
- 下載進度事件維持既有的欄位形狀（任務識別碼、進度百分比、速度或狀態文字）。分支資訊透過狀態文字欄位傳達，不新增欄位，避免破壞既有前端監聽。
- 資料庫 migration 以新版本號附加，既有版本 1 與 2 的內容不變。`download_history` 的欄位名稱與型別維持不變，僅變更 `created_at` 的預設值來源。
- 下載命令的錯誤回傳型別不變（仍為字串錯誤），僅內容由固定字串改為包含來源工具輸出。

#### 失敗模式

- 更新檢查失敗（網路不可用、manifest 不存在、驗簽不通過）：不阻擋應用程式啟動，不彈對話框，寫入錯誤 log。
- `ffprobe` 判斷失敗或無法解析輸出：視為「不確定是否相容」，走重新編碼路徑（保守預設），不因判斷失敗而讓下載失敗。
- remux 失敗：回報錯誤並清理暫存檔，不靜默留下不完整輸出。
- 歷史紀錄狀態寫回失敗（資料庫暫時不可用）：不覆蓋原始的下載失敗原因，原始錯誤仍需傳達給使用者。
- migration 執行中斷：資料複製完成後才移除舊表，確保中斷時不會遺失既有紀錄。預設值變更與既有資料回填必須在同一個 migration 版本內完成，不得分屬兩個版本 —— 否則會產生無法分辨時區的混合資料，且無安全修復路徑。

#### 驗收條件

- `cargo test` 全數通過，且新增覆蓋以下純函式邏輯的單元測試：remux 相容性判斷（涵蓋 h264 加 aac 偶數尺寸為可 remux、非 h264 為不可、奇數尺寸為不可、無音訊軌為可、ffprobe 輸出無法解析為不可）。
- `npm run check` 的錯誤數由目前 2 個降為 0（其中一個正是 async `onMount` 的型別錯誤，修好監聽生命週期即消除）。
- 公鑰欄位內容經 base64 解碼後不含 secret key 字樣，且不含 KDF 欄位 —— 可用一行解碼指令人工確認。
- 版控中不存在新私鑰：對 repo 全文搜尋不應出現新私鑰字串。
- 時間戳修復需以一筆本地時間 00:00 至 08:00 之間建立的紀錄驗證顯示日期正確；既有紀錄校正需比對 migration 前後的顯示日期。
- 事件監聽修復需以實機操作驗證：在下載頁與設定頁往返兩次後拖入一個檔案，轉檔清單只增加一筆。
- 自動更新需以一次真實發佈驗證：從修復版之前的版本觸發檢查並完成安裝，或至少確認檢查回傳有效的更新資訊且驗簽通過。

#### 範圍邊界

**在範圍內**：上述 11 項決策所涵蓋的變更，以及為驗收所需的單元測試。

**不在範圍內**：Non-Goals 一節列出的所有項目。特別註明兩項容易在實作時擴散的相鄰工作 —— 一是不要順手把其他 `println!` 改為 log plugin，二是不要順手為其他 `alert` 或 `confirm` 呼叫改成應用內提示，即使實作過程中會經過那些程式碼。

#### 部署順序

1. 人工產生新金鑰對並寫入 GitHub Secrets（阻擋後續 A 組驗證）。
2. 合併程式碼修復與設定變更。
3. 提升版本號，推送版本 tag 觸發發佈，產出正式 release 與 manifest。
4. 驗證自動更新可從修復前版本升級成功。
5. 在發佈說明中告知使用者：既有 0.1.3 安裝需手動下載一次，之後自動更新才會接上。

## Risks / Trade-offs

- **公鑰填錯或 manifest 名稱不一致，自動更新仍然失效** → 驗收要求以真實發佈實測一次升級，而非只確認設定看起來正確；且更新檢查失敗已改為寫 log，再次失效時有徵兆。
- **指向最新發佈的資產 URL 不會解析到 draft 或 pre-release** → 發佈設定需產出正式 release；此約束已寫入決策，驗收步驟包含確認 manifest 實際可被取得。
- **輪替金鑰使既有 0.1.3 安裝無法自動升級** → 既有自動更新本來就不能運作，實質上沒有功能損失；發佈說明明確告知需手動下載一次。
- **新私鑰再度被寫進版控** → 文件明確載明公鑰欄位只放公鑰檔內容，驗收條件包含對 repo 全文搜尋新私鑰字串。
- **migration 重建資料表期間中斷導致紀錄遺失** → 先完成資料複製再移除舊表；tauri-plugin-sql 的 migration 以版本控制只執行一次。
- **時間戳校正對已是本地時間的資料重複偏移** → migration 依版本只執行一次；校正使用 localtime 修飾詞而非寫死位移，跨時區同樣正確。混合時區資料的唯一成因是預設值變更與回填被拆到不同 migration 版本，因此該原子性被列為決策的硬性約束，並由驗收同時檢查既有列與新建列。
- **remux 判斷過寬導致產出無法播放** → 相容條件收斂為明確白名單，任何不確定情形（含 `ffprobe` 判斷失敗）一律退回重新編碼；重新編碼路徑保留不刪，可隨時退守。
- **remux 改變既有輸出特性** → 原本所有輸出都經過統一重新編碼，改為條件式後輸出特性會依來源而異。這是刻意的取捨：換來大幅縮短的等待時間與零畫質損失，而相容性由白名單條件保證。

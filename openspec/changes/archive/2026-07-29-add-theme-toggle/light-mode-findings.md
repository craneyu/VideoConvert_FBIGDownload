# 淺色模式檢視與驗證覆蓋記錄

任務 6.2 的產出。目的是讓 Non-Goals 的邊界被實際遵守：發現的問題不被靜默吞掉，也不擴張本變更。

## 淺色模式對比瑕疵

**無。**

實際在深色 macOS 上把主題設為淺色後檢視主畫面與設定頁，未發現對比不足或配色錯位。

一項曾被誤認為瑕疵、經查證後排除的現象：主畫面「加入下載」按鈕在淺色下看起來偏淡。成因是該按鈕帶有 `disabled:opacity-50` 且 `disabled={!urlInput}`，截圖時輸入框為空，屬既有的停用樣式，與主題無關。

## 實作期間發現、已納入本變更修正的問題

這兩項原本不在計畫中，但都是本變更自身的正確性問題，因此就地修正而非延後：

1. **`color-scheme` 單獨不足以讓原生控制項跟隨主題。** macOS 的 `<select>` 彈出選單是由視窗外觀繪製的原生 NSMenu，樣式表無法觸及。已改為同時呼叫 `getCurrentWindow().setTheme()`，並在 capabilities 加入 `core:window:allow-set-theme`。詳見 design 的對應決策。

2. **`setTheme` 會覆寫 `system` 模式賴以判斷的信號。** WKWebView 的 `prefers-color-scheme` 由視窗外觀推導；把解析後的具體值寫進 `setTheme` 會導致視窗被釘住後 `matchMedia` 永遠回報同一值，使用者切回「跟隨系統」時不再跟隨 OS。已改為依模式傳參（`system` 傳 `null`），並在原生外觀落定後重新解析套用。

## 已在真實 App 中驗證的項目

在 Dark macOS 上以實際執行的 VidBridge 驗證：

- 資料庫無 `theme` 列時冷啟動 → 深色（升級情境行為與變更前一致）
- 資料庫 `theme=light` 冷啟動 → 淺色（持久化與 `get_settings` → `data-theme` 端到端）
- 鍵盤操作三段式控制項 → 寫入資料庫且畫面即時改變，其他設定未受影響
- 同一個 process 內「跟隨系統 → 淺色 → 跟隨系統」→ 正確回到跟隨深色 OS
- 淺色模式下開啟原生下拉選單 → 選單為淺色外觀
- 所有設定仍在單一 800x600 畫面內（為此把轉檔與外觀改為兩欄）

## 以單元層而非真實 App 驗證的項目

兩項刻意未在真實環境操作，理由與涵蓋方式如下：

1. **`system` 模式下作業系統配色變更時即時跟隨。** 未實際切換使用者的系統外觀設定——那會改動本變更範圍之外的個人環境。改以執行層級檢查涵蓋：`system` 模式會註冊 media query listener 且在 flip 時重繪，固定模式完全不註冊 listener 因此不受影響。

2. **深色情境冷啟動不出現白色閃屏。** 未以錄影確認肉眼無閃爍。改以更嚴格的方式涵蓋：直接抽出 `build/index.html` 中實際出貨的內嵌 script 執行，驗證所有「快取值 × 系統偏好」組合都在首繪前得到正確的具體配色，包含 storage 拋錯與非法值的退路。

## 明確留在範圍外的後續事項

- **前端沒有測試 runner。** 本變更的前端驗證靠 `npm run check` 與外部一次性腳本，未進版控。若要讓這些檢查長期存在，需另開變更引入測試框架（design 已將此列為 Non-Goal）。
